# iOS 01｜Swift 语言特性、运行时与并发

Swift 学习需要同时建立两类认识：一种是类型、Optional、闭包、协议等语言特性怎样表达约束；另一种是值、对象和任务在执行中怎样被创建、共享、调度与结束。只有语法名称而没有语义，容易把代码写出来却不能预测行为；只追踪某个应用功能，又容易遗漏语言本身的知识结构。

本篇以知识清单为骨架，逐项解释作用、执行关系、常见误解与适用边界。文中的短代码用于辨明关键语义，完整写法、可运行示例与独立实验由 [swift-core](../../swift-core/docs/README.md)承接。Xcode 的窗口、日志、断点与单步操作见 [操作教程](../../ios/docs/project-started.md)，不作为本章的叙述主线。

## 知识结构与阅读顺序

Swift 语言、Swift Concurrency 与 Apple 平台调度设施不是同一层东西。Optional 是语言和标准库的数据表达，actor 是语言并发隔离模型的一部分，RunLoop 与 Dispatch 则是当前平台上的运行设施。把它们分清，才能回答“这条保证来自类型检查、任务模型，还是系统框架”。

| 集合与字符串 | 元素、索引、比较和转换分别有哪些语义与成本 |
| 控制流与模式匹配 | 分支、解构与作用域怎样约束可能的执行路径 |
| 函数与闭包 | 行为怎样作为值传递，怎样捕获状态与延长寿命 |

本篇于 2026-10-30 核对 Swift 6.4 语言资料和 Apple 官方文档。并发结论还受 language mode、默认 actor 隔离、特性开关与部署版本影响；“安装了 Swift 6.4”不等于每个模块自动采用相同设置。文中机制说明不冒充完整示例的编译、运行或设备验证。

## 类型系统与基础数据类型

### 类型检查约束什么

Swift 是静态类型语言。编译器在执行前检查声明、表达式、参数与返回值之间的类型关系。类型推断只是让编译器根据上下文补出类型，不意味着变量可以在运行中随意改成另一种类型。

```swift
var count = 3       // 此处推断为 Int
count = 4           // 仍然是 Int
// count = "four"   // 类型不匹配
```

`let` 与 `var` 表达可变性，类型表达可以保存什么值，两者不能混同。值类型的 let 绑定不允许改变其值；引用类型的 let 绑定不允许改指向，所指对象的可变属性仍可能改变。由此不能把 let 简化为“整个对象图都不可变”。

类型安全能提前排除一批错误，但不能证明业务规则成立：两个参数同为 Int，仍可能把“数量”与“索引”传反。语义不同且误用代价较高时，可以引入不同自定义类型，而不只依靠变量命名。

### 基础类型各有自己的边界

| 类型或表达 | 语义与需要留意的边界 |
| --- | --- |
| `Int`、`UInt` 与固定宽度整数 | 区分有符号与无符号、存储范围和溢出；普通整数运算不自动提供任意精度 |
| `Float`、`Double` | 用有限精度表达浮点数；十进制金额等需求要另核对表示与舍入规则 |
| `Bool` | 条件值；不能把任意整数直接当作布尔条件 |
| `Character`、`String` | 按 Unicode 字符语义组织文本，字符、编码单元和字节数量可能不同 |
| 元组 | 把多个值作为一个组合返回或传递；复杂且稳定的领域含义通常更适合命名类型 |
| `Void`、`Never` | 前者表示没有有用的返回数据，后者表示不会正常返回；都不等同于 Optional 的 nil |

Swift 不在普通赋值中任意隐式转换数值类型。显式转换也不自动等于安全：需要判断范围、精度和是否允许截断。整数溢出、数组越界等仍可能成为运行失败。

`is` 检查类型关系，`as?` 将可能失败的转换表达为 Optional，`as!` 则由程序员承诺一定成功，承诺错误会失败。`Any` 和 `AnyObject` 提供更宽的容器或接口，却减少调用处可直接使用的静态信息；不能通过大量强制转换恢复本来就应该由类型表达的契约。

## 空安全与 Optional

### 缺失进入类型，而不是藏在约定里

某个字段可能不存在、字典可能查不到键、文本可能无法解析为数字。如果把它们统一替换成空字符串或 0，使用方将无法区分“有一个合法值”和“没有取得值”。Optional 把这种差异放进类型：`T?` 是 `Optional<T>`，有值时携带 T，没有值时为 nil。

```swift
let parsed: Int? = Int("三个")
let displayed = parsed ?? 0
```

这里 `parsed` 缺失，而 `displayed` 是调用方主动选出的默认值。默认值适合有明确兜底含义的显示场景；用于输入校验时，可能掩盖解析失败。空安全负责要求处理缺失路径，不替业务决定缺失意味着什么。

### 解包表达不同的控制流

| 方式 | 执行含义 | 适用条件与风险 |
| --- | --- | --- |
| `if let` | 有值时进入分支，并在分支内使用解包值 | 适合局部成功路径，缺失可以走另一分支 |
| `guard let` | 缺失时离开当前作用域，成功后继续使用解包值 | 适合后续逻辑必须满足的前提 |
| `?.` | 链上遇到缺失则跳过后续访问或调用 | 适合允许缺失传播的访问链，不能代替错误记录 |
| `??` | 缺失时求取并使用默认表达式 | 默认值必须有业务含义，右侧不是无条件执行 |
| `!` | 假定有值，缺失时运行失败 | 需要可证明的不变量，不能只为消除编译诊断使用 |

隐式解包可选类型主要为某些初始化或互操作场景提供便利，它仍可能缺失，并没有获得“永远不为 nil”的保证。与 Objective-C 交互时，声明的空值标注是否可信也需要检查。

嵌套 Optional 可能表达两层缺失。例如值类型本身为 Optional 的字典，查询结果还要表达“键是否存在”。这两层可以分别表示“键不存在”和“键存在但保存 nil”，不应未经判断就展平。

Optional 只表达有无，不携带失败原因。需要区分格式错误、权限不足或资源不存在时，应进一步选择错误类型或带状态的结果。

## 集合、字符串与标准库抽象

### 数据结构决定允许的操作

Array 按位置组织元素，Dictionary 按键查找值，Set 维护不重复元素。Dictionary 和 Set 要求相应键或元素满足 Hashable；哈希用于定位候选，最终仍需依据相等语义判断，不能把哈希值当成永久唯一身份。需要排序时另定义 Comparable 或排序规则。

数组下标访问要求索引有效，返回类型不是 Optional，因此不能期待越界自动变成 nil。字典查找则天然可能没有对应键，结果使用 Optional。相同的方括号写法不意味着失败语义相同。

String 的索引也不应按数组整数下标理解。一个用户感知字符可能由多个 Unicode 标量和更多编码字节构成；把字符数当作 UTF-8 字节偏移，可能在截断或与 C 接口交换数据时破坏文本。

### 转换与复制都需要理解语义

`map` 对每个元素做转换并保留数量关系，`filter` 根据条件筛选，`compactMap` 在转换后去掉缺失结果，`reduce` 汇总为累积结果。选择 compactMap 意味着允许丢弃失败项；若每条失败都需要反馈，就不能把它当成无代价的错误处理。

Sequence 提供迭代能力，但不保证任意序列都能重复遍历得到相同结果。Collection 在此基础上提供更强的索引和重复访问约束。惰性转换延迟计算，实际消费时才付出工作；它不是自动后台执行，也不必然比立即计算更快。

Swift 集合提供值语义，Array 等采用写时复制优化共享存储：赋值后的两个值应能独立修改，实现可以到真正写入时才分离存储。若元素是类实例，独立的数组值仍可能指向相同元素对象；写时复制不是对整个对象图做深拷贝。

切片通常保留对原存储的关系，长期保存一个小切片可能保留更大的底层存储。是否复制为独立数组，应结合寿命和数据规模判断，不能只看表面元素数量。

本主题还包括区间、索引失效、切片类型、集合可变性，以及字符串编码转换。具体 API 的用法和受控输入由语言实验承接。

## 控制流与模式匹配

控制流决定哪些路径允许继续，以及每条路径能使用哪些已成立的条件。if 适合分支选择，guard 把不满足前提的路径提前结束；它们的区别不只是排版，绑定值的作用域也不同。

Swift 的 switch 要求覆盖可能情况。枚举把有限状态及每种状态的数据一起表达后，switch 可以让编译器检查是否遗漏分支，而不是靠多个可独立变化的布尔值拼出隐含状态。

```swift
enum LoadState {
    case idle
    case loaded([String])
    case failed(String)
}
```

这个类型将数据与其所属状态关联。与“isLoaded、error、items 三个字段分别可写”的设计相比，它能排除一部分矛盾组合；但关联值本身的规则仍需校验。跨模块可演进枚举还有新增成员的兼容性问题，需要结合 `@unknown default` 等规则判断，不能把所有 switch 都当成永久封闭集合。

模式匹配不仅比较相等，还能解构元组、提取枚举关联值、绑定 Optional 内容，以及附加 where 条件。`if case`、`guard case`、`for case` 把相同模式能力用于条件、前提和遍历筛选。

`defer` 将清理关联到当前作用域退出，已执行注册的 defer 按逆序运行。它适合配对的释放动作，但不会让从未进入的作用域执行清理，也不能保证在进程被强杀或不可恢复陷阱时收尾。

`assert` 用于开发诊断，`precondition` 表达程序必须满足的约束，`fatalError` 结束无法继续的路径。普通 Debug／Release 和特殊优化设置对检查的保留不同；用户输入错误应采用可恢复表达，而不应直接依赖触发陷阱。

## 函数、闭包与行为表达

### 函数契约不只有参数类型

参数标签让调用处表达各参数的角色，内部参数名供实现使用；默认参数、重载和泛型约束共同参与调用解析。返回类型则约束调用者可以得到什么。函数既可以直接调用，也可以作为值保存、传给另一段代码或从另一段代码返回。

同步调用、保存回调与异步执行是不同关系。把一个闭包传给 API，只说明传递了行为；接收方可以立即调用，也可以保存到以后调用。实际时机、调用次数和执行上下文由 API 契约决定。

### 捕获改变数据与寿命的关系

闭包能使用创建位置的局部上下文。捕获可变局部变量时，后续调用可能观察到变量的新值；捕获列表可以在创建闭包时显式保存一个值。

```swift
var count = 1
let current = { count }
let snapshot = { [count] in count }
count = 2
// 此后调用：current() 为 2，snapshot() 为 1
```

这段代码说明单线程语义，不证明多个线程可以同时读写 count。捕获列表捕获的是值；若值是类引用，保存引用并没有复制对象内部状态。

`@escaping` 表示闭包允许在接收它的调用返回之后继续存在，因此可能延长捕获对象寿命。它不表示一定异步，也不表示自动线程安全。`@autoclosure` 将一个表达式包装成可延迟求值的行为，同样不自动创建任务。

`inout` 允许函数在调用范围内对实参进行可变访问，其语义包含独占访问约束，不能简单当作可任意保存的裸指针。对同一存储进行重叠读写可能被编译器拒绝或触发运行期检查。

选择函数与闭包表达时，需要同时明确输入输出、行为是否保存、调用次数、捕获关系和结束条件；只解释尾随闭包怎么缩写还不足以理解这份契约。

## 自定义类型、成员与访问控制

### struct、class、enum 分别表达什么

| 构造 | 主要语义 | 典型选择依据 |
| --- | --- | --- |
| `struct` | 值语义，通过值传递和修改组织状态 | 一份数据应能独立替换或复制，不依赖共享身份 |
| `class` | 引用语义，多个持有者可观察同一对象 | 需要稳定身份、共享可变状态、继承或框架互操作 |
| `enum` | 在若干互斥情况中选择一种，可携带关联值 | 需要表达有限状态及各状态专有数据 |

不能因为结构体与类都能有属性、方法和初始化器，就认为二者只差能否继承。最关键的区别是赋值后的共享关系，随后才是继承、反初始化和平台要求。值类型也可能包含引用，其内部对象仍需单独分析。

存储属性保存状态，计算属性在访问时计算结果，属性观察器响应赋值，lazy 推迟初始化。计算属性不自动缓存，lazy 也不自动保证并发首次访问安全；若依赖只初始化一次的跨线程保证，需要额外同步模型。

实例方法作用于实例，类型方法作用于类型；结构体或枚举的方法需要修改自身时使用 mutating。下标提供索引式访问表达，并不取消边界和失败语义。

### 初始化和边界约束对象可用性

初始化必须在值被使用前建立有效存储与状态。类还有指定／便利初始化器及两阶段初始化规则，避免尚未完成自身状态建立时就把不完整实例交给外部。可失败初始化使用 Optional 表达无法构造，可能需要原因时则考虑可抛错初始化。

访问控制约束谁能依赖一个声明：private 与 fileprivate 的边界不同，internal 以模块为界，package 以包为界，public 对外提供使用接口，open 还涉及模块外继承或重写能力。公开更多成员会扩大需要维护的契约，不是消除访问错误的通用办法。

扩展用于补充已有类型的能力与遵循，不能像继承那样任意增加存储状态。嵌套类型和自定义运算符可以改善表达，但应以读者能稳定理解为前提。

属性包装器封装属性访问与存储相关模式，结果构建器转换特定代码块的组合表达，宏在编译期参与代码生成。三者不是同一种机制；框架声明采用哪一种还受 SDK 版本影响。学习语言能力后，再单独核对 SwiftUI 等框架的具体规则。

## 协议、泛型与抽象

### 复用行为时，哪些类型关系需要保留

协议声明一组能力要求，具体类型通过遵循来满足要求。协议扩展可以提供默认实现和派生能力，关联类型则表达“这种能力还关联哪一种数据”。它们让复用围绕所需能力展开，而不要求所有实现继承同一个基类。

泛型参数由调用处确定具体类型，约束限定该类型必须满足的能力。多个参数共享同一泛型参数时，接口还能表达它们必须是同一种类型。若简单改成 Any，调用处虽然更宽松，实现却失去这类关系，需要运行时转换补救。

```swift
func same<T: Equatable>(_ left: T, _ right: T) -> Bool {
    left == right
}
```

这里的重点不是泛型括号，而是：实现只依赖 Equatable 能力，同时 left 与 right 保留共同的 T。where 和条件遵循可以表达更复杂约束，但约束应来自实际需要，不能为了抽象提前堆出难以满足的类型关系。

### some 与 any 隐藏信息的方式不同

| 表达 | 谁决定具体类型 | 保留的保证 |
| --- | --- | --- |
| 泛型参数 `T: P` | 调用方在满足约束的范围内选择 | 参数、返回值等位置可以保留同一个 T 的关系 |
| 返回 `some P` | 实现方决定该声明背后的具体类型 | 对外隐藏名称，仍保留固定的底层类型身份 |
| `any P` | 容器在运行时可装入不同遵循类型的值 | 使用协议暴露的能力，不承诺始终是同一具体类型 |

some 不能理解为每次随意返回任意遵循类型。any 则方便异构存储和运行时替换，但会隐藏更多静态关系，并可能引入间接访问或装箱成本；具体分配和优化需要按产物验证，不能一概断言必定堆分配或必定很慢。

协议要求的实现与只在扩展中增加的方法，在派发规则上也有差别。调用处看到的静态类型、方法是否为协议要求、类继承以及优化共同影响选择；不能把“用了协议”直接等同于一种固定派发方式。

类型擦除进一步把具体实现包装在稳定接口后面，适用于需要隐藏复杂类型、统一存储或维持接口兼容的边界。代价是转发、类型信息损失和额外实现责任，是否需要应由边界需求决定。

## 错误处理与失败表达

### 先判断失败属于哪一种情况

| 表达 | 适合的含义 | 使用方需要承担什么 |
| --- | --- | --- |
| Optional | 值可能缺失，暂不需要区分原因 | 处理有值和缺失两条路径 |
| `throws` | 操作可能失败，需要传播或处理原因 | 用 try 标记潜在失败，捕获或继续传播 |
| `Result<Success, Failure>` | 成功或失败需要作为一个值保存、返回或组合 | 显式消费结果并保留错误类型 |
| 前置条件或陷阱 | 程序违反不变量，无法按当前契约继续 | 修正调用或设计，不能期待普通错误恢复 |

Swift 抛错沿调用关系传播，不等于另开线程，也不能把它泛化为任意异常都可以 catch。强制解包失败、越界等陷阱不是普通 Error；程序已经终止的路径不能指望 do-catch 收尾。

`try?` 把抛错转换为 Optional，调用方因此放弃了具体原因；`try!` 表示承诺不会抛错，承诺不成立会失败。两者都在改变失败契约，不能只为了缩短代码使用。

### 错误传播与清理是两种责任

函数可以在取得资源后注册 defer，让正常返回和抛错离开作用域时走同一条清理路径。已经被取消但尚未退出的任务不会仅凭取消标记就执行 defer；退出时机仍取决于工作是否配合终止。

`throws` 默认允许传播任意 Error；typed throws 可以限制抛出的错误类型，适合需要稳定失败集合的接口，但错误合并和跨层转换也必须满足该限制。`rethrows` 则表达抛错与接收的可抛错行为之间的联系，不能当作任意内部抛错的替代写法。

异步取消与业务失败也要区分。取消通常表示调用方不再需要工作，并不必然意味着服务异常；底层 API 可能通过 CancellationError、自己的取消错误或其他契约表现。上层应核对实际 API，而不是把每个错误都转成“网络失败”，或在错误路径中吞掉取消后无限重试。

## 值语义、所有权与内存管理

### 独立的值与共享的对象

值语义关注的是修改关系：复制一个值之后，对副本的修改不应无意改变原值的自身状态。引用语义关注共同身份：两个引用可以指向同一对象，通过一个引用修改对象，另一个引用也能看到变化。

```swift
struct Point { var x: Int }
var first = Point(x: 1)
var second = first
second.x = 2
// first.x 仍为 1
```

这个保证不要求一定按字节立即复制，也不要求值一定存放在栈上。编译器和标准库可以采用共享存储、写时复制、内联或其他优化，只要不破坏可观察语义。比较成本时应固定输入和产物，而不凭 struct 或 class 名称直接判断性能。

如果结构体保存一个类引用，复制结构体只复制了这条引用关系，并不自动复制被引用对象。Array 中保存类实例也有同样边界。需要真正独立的可变状态时，要分析整个可变对象图，而非只把外层容器改成 struct。

`==` 表达由类型定义的相等关系，`===` 检查类对象是否为同一身份。两个不同对象可以值相等，同一个对象也可以随时间改变内容，不能把二者混作缓存或更新判定的唯一依据。

### ARC 维护存活，不代替资源协议

ARC 管理类实例的强引用关系。只要还存在有效强持有，实例就不能被释放；不再被需要且强引用归零后，实例才能结束生命并执行相应反初始化。它不同于周期性扫描对象可达性的追踪式 GC。

```mermaid
flowchart LR
    A[对象 A] -->|强持有| C[保存的闭包]
    C -->|强捕获| A
```

图中的强引用环使两者互相维持存活，即使外部已不再使用它们。weak 不增加强引用计数，并在对象释放后变为 nil，适合允许对方提前结束的关系；unowned 也不强持有，但要求访问时对象仍然有效，判断错误会带来运行失败。它们表达寿命约定，不是随意消除编译器警告的修饰词。

闭包不一定应该弱捕获：如果操作必须在完成前持有其执行对象，强捕获可以符合所有权设计；如果对象保存闭包且闭包反过来持有对象，则需要消除环或明确在何时解除。仅在闭包开头把 weak self 提升为强引用，也可能将持有延长到之后的挂起点与操作结束。

对象释放、任务取消、订阅终止、文件关闭是不同事件。依靠 deinit 可以提供最后的清理出口，但不能代替“何时结束不再需要的工作”的显式规则。

### 内存安全与所有权表达

Swift 对类型、边界和独占可变访问提供检查。UnsafePointer 等接口为互操作和底层操作提供能力，同时把存储有效性、范围、初始化与释放责任交给使用者；安全语言边界外的错误不会自动被 ARC 修复。

`borrowing`、`consuming` 与非复制类型进一步表达值怎样被借用、转移或限制复制，适合具有明确唯一所有权或复制成本约束的数据。学习顺序应先理解普通值、引用和作用域，再深入这些所有权构造，不能把 consuming 误认为“立刻释放对象”。

## 同步、异步、阻塞与并行

### 这些词描述不同维度

| 概念 | 描述什么 | 不能据此推断什么 |
| --- | --- | --- |
| 同步 | 当前调用通过正常返回或抛错交回控制，调用方再继续 | 工作一定发生在主线程，或一定非常快 |
| 异步 | 完成可以发生在以后，控制流通过回调或挂起恢复衔接 | 自动并行、自动后台执行 |
| 阻塞 | 等待占住当前执行线程，使其不能继续承担其他工作 | 等待期间没有其他线程在工作 |
| 挂起 | 保存任务继续执行所需的状态，暂时让出当前执行机会 | 任务已结束，或恢复后必定换线程 |
| 并发 | 多个工作在重叠的寿命中交错推进 | 必定在不同 CPU 核上同时执行 |
| 并行 | 多个工作实际同时执行 | 结果顺序、线程安全或业务正确性自动成立 |

同步调用也可能在专门的工作线程执行。异步函数也可能长时间做同步计算；只要它没有真正挂起或转移执行条件，就仍会占用承载它的线程或 actor 执行机会。把 CPU 密集循环包在 async 函数中不会自动消除卡顿。

### await 保留依赖关系，不自动创建并发

下面仅是顺序关系示意，`operationA`、`operationB` 代表尚未给出实现的异步操作：

```swift
let a = await operationA()
let b = await operationB(a)
```

第二步必须等第一步取得 a 才能调用。await 标记潜在挂起点，允许等待期间让出执行机会；如果操作立即完成，也不要求每次都实际挂起。连续写多个 await，不会自动把这些调用改成彼此独立的子任务。

当两个工作互不依赖、希望共同推进时，再考虑 async let 或 task group。并发引入之后，完成顺序、错误合并、取消与共享数据都需要规则，不能只为看起来“异步化”增加任务。

阻塞式锁等待、信号量等待和异步等待也不同。对协作线程池使用长期阻塞，可能耗尽执行资源；把回调接口桥接到 async 时，应保存恢复点并在结果到达后恢复任务，而不是在当前线程同步等回调。

## 线程、队列与执行器

### 谁组织工作，谁实际执行

进程是运行程序的系统容器，线程是实际执行指令的调度资源，各自拥有执行栈等线程上下文。多个线程可以共享进程内存，因此“放到另一个线程”不等于隔离了对象。

队列组织工作的提交与执行关系。Dispatch 串行队列限制其工作不并发执行，并不一般性地提供一条专属线程；并发队列允许多个工作同时推进，也不承诺一项工作对应一个新线程。

| 组合 | 调用方与队列的关系 |
| --- | --- |
| 向串行队列 async 提交 | 调用方不等待完成，队列上的工作仍串行执行 |
| 向并发队列 async 提交 | 调用方不等待完成，多个工作可以重叠执行 |
| sync 提交 | 调用方等待这次提交完成；实际执行线程与队列类型需要分别判断 |

对当前串行执行关系同步等待自身，可能形成死锁。例如主线程向主队列 sync 提交并等待，而主队列又要等当前主线程工作返回。换成更多线程不一定能修复这种依赖环，应先分析谁在等谁。

OperationQueue 进一步提供操作依赖、就绪与取消等组织能力，其取消同样需要操作配合。它与 Dispatch、Swift Concurrency 可以互操作，但不是几个可以不加区分替换的名称。

### Task 与 executor 在更高一层表达执行

Task 表达一段异步工作及其状态，executor 表达它的工作片段由什么执行上下文调度。底层仍需要系统线程承载，但任务不是专属线程：任务挂起时无需一直占住某条线程，后续恢复由调度与隔离条件决定。

actor 使用串行执行语义保护隔离状态；默认并发执行器承载不要求特定 actor 隔离的相应工作。只观察一次 Thread.current，不能据此建立“这个方法永久属于这条线程”的规则，更不能跨 await 依赖线程局部存储或某次持锁的线程身份。

在 Apple UI 环境中，MainActor 与主线程紧密关联，但“当前恰好在主线程”与“编译器知道当前满足 MainActor 隔离”是两种证据。UI 接口的隔离要求应在声明和调用关系中满足，不能仅靠运行时线程判断替代静态约束。

线程安全还不等于所有并发逻辑都正确。数据竞争关注未同步的冲突内存访问；竞态条件还包括根据执行顺序不同产生错误结果。死锁、优先级反转和饥饿则描述不同的等待与调度问题，诊断前需要先辨明现象。

## 事件循环与 RunLoop

### 没有工作时等待，有事件时处理

事件循环是一种持续接收和处理事件的运行方式：线程没有可处理工作时等待；输入源、定时器等条件使它获得处理机会；处理器执行完毕后回到循环。它不是必须忙等的 while 循环。

Apple 平台用 RunLoop／CFRunLoop 管理相关事件处理。应用框架在启动时建立并驱动主线程 RunLoop；工作线程虽然可以取得关联的 RunLoop 对象，却不会因为对象存在就自动开始循环。普通 iOS 应用也不应该在主线程另开永久 run 调用去替代框架驱动。

```mermaid
flowchart LR
    W[等待与唤醒条件] --> R[获得事件处理机会]
    R --> H[在所属线程执行处理器]
    H --> N[结束当前处理并继续循环]
    N --> W
```

这是整体关系示意，不规定所有事件来源的严格执行次序。RunLoop 的输入源、Timer 和 Observer 各有职责：输入源提供待处理事件，Timer 提供到期检查与调用，Observer 用来观察循环阶段；不能把 Timer 与所有输入源简单当作同一类型。

### mode 与忙碌会改变什么时候处理

RunLoop 每次在某个 mode 下运行，该 mode 决定参与本次处理的源与定时器等集合。只在 default mode 注册的 Timer，不会因为 RunLoop 正在其他 mode 中运行就自动得到处理。common modes 是一组被标记为 common 的模式及注册关联机制，不是一个代表“所有模式”的永久执行线程。

Timer 也不是实时保证。到期时线程可能正在执行长任务，或循环处于不监控该 Timer 的 mode，处理就会延迟。改变注册模式只能处理一部分原因，不能修复处理器本身长期占用线程的问题。

主线程处理一个耗时回调期间，无法同时在同一线程继续处理后续交互。这里可能发生的是主线程持续计算，也可能是它阻塞等待别处；两者都能让界面无响应，治理方式却不同。更深入的诊断进入第 08 篇。

### 与 Dart 事件循环的比较边界

Dart isolate、JavaScript microtask／event queue 和 iOS RunLoop 都能帮助讨论事件与异步，但它们属于不同运行模型。不能把一个平台的微任务优先级规则直接搬来预测 Task、Dispatch 和 Timer 的全部顺序。

RunLoop 管理相关线程的事件处理，Dispatch 管理队列工作，Swift Concurrency 管理任务与隔离执行。三者有底层协作，并不意味着“所有 async 都排入同一条 RunLoop 队列”。先说明 API 契约、依赖和隔离条件，再根据需要观察实际调度。

## Swift Concurrency 与任务生命周期

### 结构化并发把工作与作用域连接起来

异步函数在任务上下文中执行，调用一个异步函数并不等于另建一项独立任务。需要多个子工作时，async let 适合数量明确的子任务，task group 适合按输入动态增加和收集子任务。

结构化并发的重要保证是父子关系和作用域约束：子工作不能在结构化作用域结束后无主地继续存活，调用方需要等待它们终结。结果通常按消费逻辑汇合；task group 的完成结果不能假定按添加顺序出现，若顺序有意义应携带身份并显式整理。

错误传播也要明确观察点。抛错子任务失败后，组内其他任务不应被想当然地视为已经全部停止；错误怎样被 next 或遍历消费、组闭包是否抛错退出，以及是否主动取消剩余任务，会影响后续行为。抛错退出作用域时仍需等待子任务终结，取消不是强制销毁线程。

### 非结构化任务需要显式拥有者

`Task {}` 用于建立非结构化任务，在符合条件时继承调用处的 actor 上下文、优先级和 task-local 值。`Task.detached` 不继承相同的 actor 上下文和 task-local 值，适合确实需要脱离该上下文、且输入和寿命规则已独立明确的工作。

两者都不能仅凭“写在函数内部”就视为结构化子任务。创建者返回或被取消，并不自动为一个非结构化任务建立完整结束关系；需要由拥有者决定是否保存句柄、何时取消、怎样接收结果。detached 也不是“需要后台工作”的默认答案。

任务优先级提供调度信息，不保证确定的线程、执行顺序或实时期限。yield 提供让出机会，异步 sleep 挂起等待，这些操作都不能当作与另一个任务建立确定先后关系的同步协议。

### 取消是请求，终结需要合作

调用 cancel 记录取消请求并按任务关系传播；工作需要在恰当位置检查 `Task.isCancelled`、调用 `Task.checkCancellation()`，或使用会响应取消的 API。CPU 循环若从不检查，可能继续运行；外部设备或回调操作也可能需要额外取消接口。

取消处理器负责响应取消事件，普通执行路径负责正常推进与退出，二者可能竞争。清理动作需要幂等且有明确同步规则，不能无保护地修改同一资源状态。

“已请求取消”“任务已观察取消”“任务已终结”“底层资源已关闭”是四个不同阶段。需要释放完成的保证时，还要等待任务或资源协议的相应终结信号。

### 回调桥接和异步序列仍有资源责任

continuation 保存异步调用的恢复点，把一次回调结果接回挂起的任务。单次 continuation 必须恰好恢复一次；漏恢复会使等待无结果，重复恢复违反约束。checked continuation 的诊断能力不能替代“成功、失败、取消谁有权恢复”的状态设计。

AsyncSequence 表达随时间逐项到达的值，消费方通过异步迭代取得元素。AsyncStream 可以桥接推送来源，但缓冲策略、生产结束、消费取消与底层订阅注销仍要分别约定。默认能缓冲不等于已经具备背压；慢消费者与高速生产者的资源成本需要按具体序列和策略判断。

## actor 隔离与并发安全

### 串行隔离保护访问，不包办整个业务事务

actor 让受其隔离的可变状态在受控的串行执行片段中访问。跨隔离调用可能需要 await；当方法挂起时，actor 可以处理其他工作，因此恢复后此前读到的状态可能已经改变。

```swift
actor Inventory {
    private var available = 1

    func reserve(after check: @Sendable () async -> Void) async -> Bool {
        guard available > 0 else { return false }
        await check()
        guard available > 0 else { return false } // 恢复后复核
        available -= 1
        return true
    }
}
```

假设两个调用都在第一次检查后挂起，若省略恢复后的复核，两者都可能按旧判断继续扣减。actor 可以消除这一状态的并发冲突访问，却不能自动让跨挂起点的整段业务变成事务。这就是可重入性带来的设计问题：需要复核、版本号、预留状态或其他显式协议，具体选择由业务约束决定。

### 隔离与跨域传递分别检查

MainActor 或其他 global actor 表达一组声明共享的隔离域；实例 actor 各自拥有隔离状态。isolated 与 nonisolated 用于表达具体访问或调用的隔离关系，nonisolated 不意味着可以随意访问 actor 的可变成员。

Sendable 表达值可以按所规定的安全方式跨并发隔离边界传递，`@Sendable` 对函数值及相关捕获施加约束。它不意味着任意对象内部读写都会自动加锁。需要在对象之间转移独占使用权时，sending 等构造还会影响编译器对后续访问的检查。

Swift 6 language mode 加强数据竞争诊断，但结果仍受声明、导入模块、unsafe 边界和互操作条件影响。`@unchecked Sendable`、`nonisolated(unsafe)` 等绕过检查的表达，把证明责任交给实现者，不能作为处理诊断的常规快捷方式。

### 执行位置需要版本与配置条件

Swift 6.2 引入了可选择的默认 MainActor 隔离，以及让相应非隔离 async 函数留在调用方执行上下文的迁移能力；`@concurrent` 用于显式选择相关并发执行语义。这意味着旧资料中“nonisolated async 一定切到通用执行器”的说法不能脱离特性设置沿用。

分析代码时需要一起记录 compiler 版本、language mode、默认隔离和相关特性开关；框架声明是否带 actor 标注也会影响调用处。不能只看 async、Task 或 nonisolated 的拼写就宣布一定在后台线程。

锁适合短而明确的同步临界区，actor 适合用隔离接口组织共享状态，不可变值则能减少同步需求。不要持有要求线程配对解锁的锁跨 await：任务恢复不保证原线程，其他工作还可能因等待该锁占用协作执行资源。锁与 actor 解决的问题有交集，选择要联系等待方式、寿命与访问协议。

## 正文、示例与验证的分工
